# 2026-11-13 news

Ten days, 137 items fetched. The theme is **contracts a machine can't quietly break**: test data a coding agent can't weaken, version numbers that change how carefully an agent checks an upgrade, idempotency keys that make a replayed agent step safe, and tokens that record which agent acted for which user. Two Martin Fowler articles carry most of the weight. There is also a Postgres core CVE that affected every managed Postgres platform.

Each item is marked with the objective it serves.

## Security

### CVE-2026-6460: privilege escalation to RCE in PostgreSQL core
*Objective: none (security issue in a platform I use)*

[Mehmet Ince's write-up](https://mehmetince.net/part-3-6-how-i-ended-up-turning-a-22-year-old-postgresql-type-confusion-primitive-into-rce-cve-2026-6460/) documents a class of **type-confusion** bugs in Postgres core, present since 2004. What makes this one serious:

- It is triggerable by **the lowest-privileged login role** — no extensions, no superuser, no special grants. The root cause is that a prepared statement can retain a value whose composite-type attribute is altered to an incompatible type before execution, so the output function reinterprets attacker-controlled bytes. That mismatch is a reliable memory-corruption primitive, and the researcher drove it to code execution.
- **Every managed Postgres offering he tested was affected**, including AWS Aurora/RDS, Azure Database for PostgreSQL, Google AlloyDB (escalated to P0), Supabase, Neon and other Postgres-compatible products. You cannot outsource this risk to the managed layer.
- The **9 November 2026 Postgres release** fixed it as part of a 52-CVE batch. Six of those CVEs trace to this research. The umbrella fix (CVE-2026-6460) adds composite-attribute versioning; the others close related `RECORD`/typmod, statistics-import and tuple-size variants.

Action: take the minor release on anything you self-host, and confirm your managed provider has patched. This is the same escalation shape as [[sql-injection]] — a low-privilege foothold into the database engine becoming code execution — and reinforces the [[Partitioning scheme]]/least-privilege point that a login role is not a safe trust boundary. See also [[postgres tricks]], [[Postgres advisory locks]].

### Querying data the database can't decrypt (SQL Server Always Encrypted)
*Objective: AI-augmented systems (adjacent), none primarily*

A [Microsoft research retrospective](https://devblogs.microsoft.com/azure-sql/how-do-you-run-a-query-against-data-the-database-cant-read) on Always Encrypted (SIGMOD 2020) is a clean primer on the "strong adversary" threat model — an attacker who owns the running server and can attach a debugger. Worth it for the concrete mechanics:
- **Column Master Key / Column Encryption Key** split: the CMK lives in your Key Vault or HSM and never reaches the server; the server only ever holds the data and the encrypted CEK. This is exactly the KEK/DEK pattern in [[Hybrid and envelope encryption]].
- **Deterministic** encryption allows equality and B-tree indexing but leaks value frequency; **randomized** leaks nothing beyond length but can't be queried.
- **Secure enclaves** + **attestation** reopen range/`BETWEEN`/`LIKE`: encrypted values are decrypted only inside an attested memory region the host OS and admins can't inspect, and the client checks the enclave's signature before releasing keys. The paper is honest about residual leakage (deterministic leaks frequency, enclave range leaks ordering). TPC-C cost: ~64% of baseline for the metadata round trip even before encryption overhead. Connects to [[HTTP Security Headers]] / [[Web Security]] on "encrypted is not binary".

## AI-assisted development

### Tests as data: keeping AI-written tests trustworthy
*Objective: AI-assisted development*

[Martin Fowler / Pietro Martinelli, "Tests as data"](https://martinfowler.com/articles/tests-as-data.html) is the most actionable read of the period. The problem it names is one I'll hit directly: when the agent writes both the code and the tests, and refactors both as features land, you stop trusting that the tests still pin the right behaviour. The proposal:

- **When AI writes the code, the developer becomes the customer.** So *customer/acceptance tests* (black-box, in the language of the domain), not unit tests full of mocks, become the primary contract. Mock-heavy unit tests mostly prove "function A calls function B", break on harmless refactors, and often just encode the current implementation including its bugs.
- **Move the test's essence into data, not code.** A table (CSV/YAML) of input → expected output, or a scenario DSL with `GIVEN/WHEN/THEN` state printed in a readable, diffable form. The agent cheaply writes the *runner*; the humans own the *data*. Tables make missing cases visible at a glance.
- **Constrained Tests** (Ivett Ördög): use an *external* DSL where the assertion is mandatory syntax, so an agent can't fake coverage with assertion-free tests. Then **protect the data files** — make them read-only or gate them in CI/hooks — so an unexpected change to the spec is visible in source control rather than buried in an "AI refactored the tests" diff.
- Builds on Fit / Specification by Example, Go's tabular tests, and Approval Testing. Pair with property-based tests, mutation testing and human exploratory testing; skip the machinery for throwaway prototypes.

This sharpens [[Testing strategy]] (which currently leans on mock-heavy unit tests as the default) and [[how to review code]], and it's the practical counterpart to [[AI Discernment]].

### Long-horizon agents and durable execution
*Objective: AI-augmented systems; Event driven systems*

[Fowler / Shimon Rozenzweig, "Long-horizon agents and durable execution"](https://martinfowler.com/articles/durable-execution-agents.html) treats a weeks-long agent (a stock-replenishment example) as a distributed system and shows how durable-execution runtimes (Temporal, Cloudflare Workflows, Restate, Inngest, DBOS) handle the failure modes. Strong overlap with my event-driven notes:

- **The agentic loop = goal + tools + state + model**, with the harness running the loop. Every call to the outside world is a **step** whose input/output is written to a **log**; after a crash the program is **replayed**, recorded steps return from the log instead of re-running, and state is rebuilt. The business rules live in code (`tool.allowed(state)`), not the prompt.
- **Process workflow vs entity workflow**: one durable workflow per unit of work (a replenishment) vs one long-lived per business entity (a SKU/customer) that holds state and spawns the process ones. This is a durable-execution restatement of the aggregate idea in [[Go domain model invariants]] and relates to [[Event-carried state transfer in Microservices]].
- **Idempotency is the first thing the harness must own**: retries give at-least-once, so a stable idempotency key (here the PO number) makes the external write effectively exactly-once — the same concern as [[Two-phase commits]] and the dedup logic in [[Buses and Queues]].
- Harder, non-durable problems it's honest about: **outcomes nobody sees** (the call "failed" but the order went through — needs a compensating `cancel_order`), **the world moving during a wait** (re-check price at order time, not approval time), **code change under a running task** (treat the log as a published interface, use Parallel Change to version rules), **unbounded memory** (MemGPT/Letta-style tiered context), and **prompt injection** from tool output (the model can't distinguish data from instructions). See [[EventBridge]], [[site reliablity engineering]].

### Durable execution is going mainstream on AWS too
*Objective: Event driven systems; AWS cert*

The [Serverless ICYMI Q3 2026](https://aws.amazon.com/blogs/compute/serverless-icymi-q3-2026/) backs up the Fowler piece with product news:
- **Lambda Durable Functions** SDK for .NET is GA (joining TS/Python/Java), with a bring-your-own-SDK conformance suite and a **Pydantic AI integration** that makes each model/tool call a durable step — an interrupted agent resumes instead of repeating expensive calls.
- EventBridge **relaunched the Custom event bus**: a central team shares one bus across accounts via RAM, with a chosen **retention period**, **ordering within a publisher key**, and Avro/Protobuf/JSON incl. CloudEvents. This finally gives EventBridge the durability and subscription semantics my [[EventBridge]] note explicitly says it lacks — worth updating that note.
- Lambda **public-preview runtimes** Node.js 26 / Python 3.15; SnapStart for container images; SQS provisioned mode to 10,000 pollers.

### SemVer still steers coding agents
*Objective: AI-assisted development*

[Microsoft DevBlogs, "Do AI coding agents care about SemVer?"](https://devblogs.microsoft.com/blog/do-ai-coding-agents-care-about-semver) — ~1,000 runs, byte-identical code behind different version labels. Finding: the **smaller the model, the more the label sways it**. Claude Haiku 5.5 merged a *patch*-labelled breaking change without checking 37% of the time, but a *major*-labelled one only 7%. Claude Opus 5.5, GPT-6.1 Sol and Terra checked every upgrade regardless. Every broken `main` in the study came in under a patch/minor label. Takeaway for [[Conventional commits]]: keep SemVer honest — a breaking change shipped as a patch is exactly the case where some agents skip the check.

## Cloud & platform

### AWS Emulator — official local AWS
*Objective: AWS cert; AI-assisted development*

[AWS Emulator](https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/) ([Simon Willison](https://simonwillison.net/2026/Nov/11/aws-emulator/)) is a local, no-fee emulator (Rust, open source) that speaks the real AWS APIs over `https://127.0.0.1:9297`. Point the CLI/SDK at it with env vars and your tests, scripts and coding agents run unchanged; there's an embedded mode for the Rust SDK (own state per instance, parallel-safe). Fidelity is measured against real AWS as public "k of n" scores per service. Two caveats that matter: it **does not evaluate IAM/resource policies** (so it's no security test — a request AWS denies may succeed locally), and it's single-account/single-region. On macOS/Windows it needs Docker. This is a big step beyond the SAM-only approach in [[Local development of lambda and step functions]] — that note should gain an AWS Emulator section. (Notable aside: built largely by an agent swarm — ~29,684 commits in three weeks.)

### AgentCore runtime V2 and Nitro Sandboxes
*Objective: AI-augmented systems*

- **Next-gen Bedrock AgentCore runtime is now the default** ([announcement](https://aws.amazon.com/about-aws/whats-new/2026/11/new-agentcore-runtime-default/)): snapshot-restore per session, scale-to-zero idle, each session in its own Firecracker microVM. P75 cold start **under 2s vs 29.7s** on a 2 GB image; up to 68% less billed memory for multi-turn agents. Opt an existing runtime in with `platformVersion=V2`.
- **Nitro Sandboxes** ([AWS Compute](https://aws.amazon.com/blogs/compute/nitro-sandboxes-hardware-isolation-for-every-eks-pod-ecs-task-and-ec2-workload/)): per-container hardware-isolated VM (Nitro Enclave technology, now with virtio networking/block + Firecracker) so neither the cluster admin, the platform team, nor AWS can read an EKS pod / ECS task's memory, at near-native performance. Consolidate hard-boundary workloads instead of one instance each. See [[AWS Container hierarchy]], [[kubernetes pod scheduling]].

### Cognito OAuth 2.0 token exchange (RFC 8693)
*Objective: AI-augmented systems; AWS cert*

[Cognito now does token exchange](https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/): a service or agent acting for a user swaps the user's token for a **narrower, single-audience** token with no refresh token, and an **`act` claim** records the intermediary (e.g. an MCP server) so a downstream API can tell an agent-on-behalf-of-user call from a direct one. New `GetDerivedToken` API. This is the delegation/impersonation piece my [[Identity token vs Access Token]] and [[AWS Cognito and IAM]] notes don't yet cover, and it's the auth backbone for the long-horizon-agent world above.

## Consulting & facilitation

### A four-phase workshop planning method
*Objective: Improve consulting skills (active listening, facilitation)*

[SessionLab, "How to plan a workshop"](https://www.sessionlab.com/blog/planning-a-workshop/) is a concrete, reusable process (Dragon Dreaming–derived): **Vision → Design → Action → Learn**, each with a client checkpoint. The Vision phase is the consulting-skills core and the most directly useful to my objective:
- Check for four things up front: **non-negotiables**, **tangible outcomes** (what concrete artifact exists at the end that didn't before), **intangible outcomes** (trust, connections — capture the client's own keywords), and **level of participation** (the "ladder of participation": will participant proposals be adopted, feed a later decision, or just inform a decision already made?). Naming the participation level early prevents disappointment.
- The named skills — **probing questions, active listening, appreciative inquiry** — are exactly my objective. The move is "slow the client down and inquire into motivation"; run a mini-workshop with the client. Connects to [[Communication style]] and [[Objectives and Key Results]].

### Why faster review gates are the wrong AI fix
*Objective: Improve consulting skills; AI-assisted development*

[Voltage Control, "Your Processes Are Human-Shaped"](https://voltagecontrol.com/blog/your-processes-are-human-shaped/) has data worth keeping: across 8.1M PRs (LinearB 2026), AI-generated PRs wait **>16h** before a reviewer opens them (vs ~200 min), and merge at **32.7% vs 84.5%** for manual. A second dataset (Opsera, 250k+ devs) finds AI PRs carry **15–18% more security vulnerabilities per line**. The argument: AI raised *volume at the gate* while the gate is still staffed for the old volume — so speeding it up or adding reviewers just processes more shallow passes. Instead, separate **toil** (rubber-stamp gates nobody has said no to in years) from **protective friction** (the review that actually caught something), and decide which arrivals need a human at all. This reframes [[how to review code]] and [[site reliablity engineering]] at the org level, and overlaps the "judgement is the bottleneck" thread in [[AI Discernment]].
